# Project 1：从日志定位问题到验证优化

这份文档面向第一次接触模型 Agent、Trainium 和偏微分方程的 CS 本科生。它记录实际做过的
改动、失败、对照实验和下一步判断。未完成的实验不会写成提升；后续结果追加到本文。

## 1. 我们究竟在优化什么

项目让一个小语言模型回答一维热传导问题。输入是方程、两端条件、初始温度；输出是一个
可以代入计算的 `u(x, t) = ...` 表达式。程序把答案交给检查器，失败后把错误反馈给模型重试。

流程为：题目 → 模型 → 可选计算器 → 最终表达式 → 检查器 → 下一轮反馈。

本次优化的是这个**推理时的工作流程**，没有训练模型权重，也没有修改 Trainium 内核。
Trainium 运行 Qwen3-8B；Python 在 CPU 上组织请求、调用 SymPy、评分、记录实验。
服务器用于模型推理的两个核属于模型服务的并行配置，不意味着我们要启动两个 Agent。
增加 Python 终端或同时启动更多实验也不等于增加模型算力，反而可能使请求排队。

我们希望在相同题目、评分和计算预算下，提高完成正确答案的稳定性，或者在保持正确率的
同时明显减少完成时间、轮数或模型输出量。单次成功、单轮变快、日志更丰富都不等于这项
目标已经实现。

## 3. 数学背景：为什么一个指数会让答案从 1.0 变成 0.6

热方程写作 `u_t = k*u_xx`。`u_t` 是温度对时间的变化率，`u_xx` 是温度沿杆的空间曲率；
`k` 决定热扩散速度。模型经常把解写成几个波形的叠加。

考虑其中一项：

```text
u = A*exp(-lambda*t)*sin(mu*x)
u_t  = -lambda*u
u_xx = -mu**2*u
```

代入热方程必须满足 `lambda = k*mu**2`。每一项都要使用自己正弦中的频率 `mu`，包括
分母。频率越高，衰减越快。

例如题目 1.3 的某个波形是 `sin(pi*x/2)`，`k=2`。它应搭配
`exp(-2*(pi/2)**2*t)`。日志里出现的 `exp(-2*pi**2*t)` 把频率中的 `/2` 丢掉了。
后续项也必须逐项对应；不能把“第几项”直接当成频率。

对于抛物线初始温度，单个正弦不够，需要多个波形。模型自己提出投影积分，计算器只执行
它提出的式子。计算器算对积分，并不能保证模型最后选择了正确波形或指数。

检查器的总分是四项相加：

| 检查 | 权重 | 含义 |
|---|---:|---|
| equation | 0.4 | 答案满足热方程 |
| left_bc | 0.2 | 左端满足温度或斜率条件 |
| right_bc | 0.2 | 右端满足温度或斜率条件 |
| start_shape | 0.2 | t=0 的形状足够接近题目 |

本次 0.6 的候选是后三项通过、方程失败。**0.6 是一个候选的部分得分，不是 60% 的
运行成功率。** 相同总分也可能来自其他组合，因此必须查看 `parts`。

## 4. 第一步：先让实验能够被解释

最早只有控制台分数，不能判断慢在哪里，也不能复现某次运行到底用了哪版代码。
我们首先加入 `run_experiments.py`、JSON 配置、源码快照、每次运行独立目录和汇总文件。

`agent.py` 额外记录每次模型请求的实际提示词、回复、API 时间、token 用量、结束原因、
计算请求和计算结果。这些改动主要改善可观察性，没有证明求解能力提高。

关键文件：

- `config.json`：题目、seed、候选数、重试轮数和输出预算。
- `source/`：实际运行的 Python 源码。
- `run-01/attempts.jsonl`：每行一个候选，内含多次模型/工具交换的 `trace`。
- `run-01/console.log`：控制台过程。
- `summary.json`：完成状态、成功次数、耗时和请求量。

一次候选可能先发积分请求，再接收计算结果并写最终答案。因此 4 个候选可能产生 8 次
模型请求，也可能包含 20 多个计算表达式。“工具调用表达式数”“HTTP 请求数”和
“Python 进程数”是不同指标。

4 个候选并发生成。它们的 API 时间相加不是整轮耗时，整轮主要由最慢的候选决定。
当前实现等全部候选返回才评分；提前评分和取消其他请求是另一个可研究方向，尚未实现。

## 5. 第二步：简洁工具提示词为什么没有成为优化

实验只把计算器提示词改为要求简洁的 `COMPUTE:` 请求和最终答案，其余预算保持一致。
直觉是减少无用解释和 token，缩短每轮生成时间。

| 同为 1.3、seed 0 的初次实验 | baseline | 简洁工具提示词 |
|---|---:|---:|
| 成功 | 1/1 | 0/1 |
| 使用轮数 | 1 | 4 |
| 完整耗时 | 106.3 秒 | 173.7 秒 |
| 模型请求数 | 8 | 32 |
| 输出 token 总数 | 2313 | 3632 |
| 截断回复数 | 0 | 0 |

简洁方案每轮约 43 秒，但四轮全部失败，16 个最终答案逐字相同。积分结果正确，最终
指数仍然错误。下一轮提示词确实含检查器反馈，所以错误并非“反馈忘了传入”。

结论：单轮更快不代表整个任务更快。多次失败会把节约的时间和 token 花回去。该选项
保持可选，未设为默认。只有各一次实验，不能严格证明简洁要求导致了失败。

## 6. 第三步：重复 baseline，排除一次幸运成功

使用原提示词、相同 seed 和预算连续跑三次，得到：

| 次数 | 结果 | 轮数 | 完整耗时 | 截断回复 |
|---|---|---:|---:|---:|
| 1 | 成功 | 2 | 205.325 秒 | 0 |
| 2 | 失败，最高 0.6 | 4 | 777.336 秒 | 8 |
| 3 | 成功 | 2 | 257.795 秒 | 1 |

三次共 32 个候选，9 个最终答案无法解析，5 个候选的 Markdown 包装计算请求未被严格
`COMPUTE:` 解析器识别。失败运行约 776.355 秒用于生成/工具交换，检查只有 0.424 秒。

这改变了诊断：除了指数推理错误，还有输出截断和协议不匹配；没有证据表明检查器计算
太慢。三次观察成功率 2/3 也不等于真实稳定成功率就是 67%。

`seed` 固定题目生成和检查点。当前请求没有设置模型采样 seed，模型的采样结果不会随
题目 seed 固定。因此同一个题目在不同运行中仍可能产生不同回答。即使四个候选重复，
也不能仅凭日志断言服务端忽略了采样参数。

## 7. 第四步：检查其他题型，避免只针对 1.3

仍使用 baseline、seed 0 和相同预算：

| 题目 | 结果 | 轮数 | 完整耗时 | 截断回复 | 无法解析的最终答案 |
|---|---|---:|---:|---:|---:|
| 1.1 | 成功 | 2 | 430.303 秒 | 7 | 7/8 |
| 1.2 | 成功 | 1 | 218.206 秒 | 2 | 3/4 |

1.1 的一个失败回复已经求出正确频率和第一项系数，却继续推导用不到的高阶项，直到
1200 token 用完，没有完整最终答案。这类 0 分首先是输出不完整，不能直接叫数学不会。

每题只测一次，作用是发现其他失败类型，不能证明某题已经稳定解决。Level 0 的旧自测
通过与真实模型成功率也是两件事。

## 8. 第五步：当前实验——通用解题步骤提示

新选项 `--solution-style guided` 在题目后附加一个通用方法清单：

1. 每个波形采用 `exp(-k*mu**2*t)`，明确包含频率的分母。
2. 初始条件已是符合边界的有限个波形时，保留题目给出的系数和频率，避免无用投影。
3. 其他初始形状才按题目投影公式请求积分，选择足够多的非零项。
4. 最后逐项核对频率与指数，简短解释，为完整答案留出 token。

原理是把模型容易忘记的约束放在任务上下文中，减少“中间知道、最后写错”和无用展开。
它提供一般数学方法，没有根据 `problem['exact']` 或 `series_answer()` 生成答案，没有
预填某道题的系数；具体计算仍由模型提出，检查器仍独立评分。

这是提示词/Agent 流程调优，不是模型训练。它比原始任务多了一般方法提示，不能宣称
模型在完全相同的信息条件下变聪明了。

`configs/guided.json` 与 baseline 的有效配置仅 `solution_style` 不同。输出预算 1200、
4 个候选、最多 4 轮、一次工具交换、模型采样参数和原检查器均保持一致。默认仍为
baseline，避免在验证前影响其他组员。

当前状态：11 项本地工作流测试通过；真实模型 pilot 已在独立目录启动。**结果尚未确认，
还没有证据证明这一步产生了明显优化。** 后续应把实际失败也追加到这里。

## 9. 怎样验证“明显优化”

先做 pilot 检查可运行性，再在覆盖六个子题和额外 problem seed 的固定测试集上比较。
用交错的 baseline/guided 顺序减少服务时段差异；两个方案使用相同预算和原始评分。
不能不断挑选有利 seed，把失败和超时从分母删除，或把同一轮的四个候选当成四次独立实验。

比较顺序为：

1. 完整运行成功数；失败、异常、截断与中断分别保留。
2. 包含失败运行的完整耗时，以及成功时轮数。
3. 请求数、输出 token、输出截断和各检查项失败情况。

明显提升可以是固定测试集上完成更多题，或保持成功覆盖同时明显降低完整耗时/生成量。
必须给出样本数、原始记录和局限；小样本结果只支持“这批实验观察到提升”，不支持
“所有热方程任务稳定提升”。若 pilot 失败，先定位失败环节，再决定继续提示词、协议
处理或反馈修复，不用增加测试次数来替代解决问题。

4. 最终答案有没有保留中间正确关系？
5. 下一轮提示词是否包含反馈，模型是否实际改变了错误？

## 11. 小组如何继续

共同主干是小组仓库的 `master`。每人负责一个功能分支，通过英语 PR 审查后合并。
实验/日志、Agent/工具、数学反馈/验证、整合/展示可以由四人分别负责。

目前 `challenge1-improvements` 有另一个改进 Agent 和额外验证器；本分支有实验运行器。
整合时先统一命令和记录格式，再公平比较。额外验证的结果应单列；不能把使用不同检查器
的两个成功率直接当作算法优劣。

每个改动都要回答四个问题：改了什么？日志中什么证据支持它？同预算对照结果是什么？
下一次失败会如何定位？把负面结果留下来，也是避免全组重复踩坑的一部分。
