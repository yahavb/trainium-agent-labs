# Numerics and dtypes

- Use only float8_e4m3/float8_e5m2/bfloat16/float16/tfloat32/float32 (plus float8_e4m3fn on trn3) as nc_matmul inputs, and never mix legacy float8_e4m3 with OCP float8_e4m3fn. FIX: Quantize/cast to a supported float dtype before the matmul; on trn2 use nl.float8_e4m3 (legacy), on trn3 prefer nl.float8_e4m3fn.
- Set is_transpose=True for identity-matmul transposes; on trn2+ it is bit-accurate (NaN/Inf preserved), on trn1 it only tags the op for the profiler. FIX: On trn1, replace NaN/Inf with finite sentinels before PE transpose, or use Vector Engine nc_transpose for <=32x32 tiles.
- Feed nc_matmul_mx packed x4 operands (float8_e5m2_x4, float8_e4m3fn_x4, float4_e2m1fn_x4) with float8_e8m0fnu scales and an fp32 or bf16 PSUM dst. FIX: Produce operands with nisa.quantize_mx (bf16/fp16 -> x4 + e8m0fnu scale) or load pre-packed data via dma_copy.
- Expect dma_copy with differing dtypes to cast src->fp32->dst, except under dge_mode=hwdge where dtypes must match exactly. FIX: Use dge_mode=none/swdge for casting copies, or .view(dtype) to reinterpret bytes under hwdge.
- Do not use int32/uint32 tiles as input or output of tensor_scalar_cumulative; op1 must be add/subtract/mult/max/min. FIX: Compute in fp32/int16 and cast, or use iota-based arithmetic.
- When range_select writes a bf16/fp16/fp8 dst, keep reduce_res in fp32 so a fully-masked row (-inf after downcast) does not produce NaN in the following activation subtract. FIX: reduce_res = nl.ndarray((P,1), nl.float32, buffer=nl.sbuf).
- Rely on Vector/Scalar/GpSimd/DMA compute performing math in fp32 with a free cast to dst.dtype; do not add separate cast instructions. FIX: Allocate dst in the desired dtype and let the op cast.
- Use nl.float8_e4m3fn (OCP) only on trn3; on trn1/trn2 use legacy nl.float8_e4m3 (max 240) or set the UNSAFE_FP8FNCAST escape hatch for torch.float8_e4m3fn inputs. FIX: Convert to nl.float8_e4m3 or bf16 before the kernel on trn2.
- Request dtype=nl.uint8 (bool_) from comparison ops when the result feeds a predicate; nl.where expects float 1.0/0.0 conditions. FIX: mask = nl.greater(x, 0, dtype=nl.uint8).
- Avoid tfloat32 for activation bias, select_reduce on_true, and as a general storage type; use it only as a matmul operand precision. FIX: Store in fp32/bf16.
- Rely on FP32 accumulation inside TensorE/PSUM regardless of input dtype; before Trainium3 the matmul output in PSUM is always FP32 (except transpose mode). FIX: psum = nl.ndarray((M,N), nl.float32, buffer=nl.psum); downcast during eviction (tensor_copy to bf16 SBUF).
- Downcast FP32 matmul operands to BF16/FP16/TF32 (or FP8) before nc_matmul; FP32 inputs run ~4x slower (20 vs 79 TFLOPS on trn2). FIX: Cast during load/eviction (tensor_copy dtype=nl.bfloat16) and keep weights in bf16 in HBM.
- Store VectorE/ScalarE intermediates in bf16 freely: arithmetic is always FP32 internally with zero-overhead input/output casting, so low-precision storage costs no accuracy inside the instruction. FIX: Use bf16 SBUF tiles between instructions, fp32 only for running accumulators that need it.
- Choose FP8 formats deliberately: FP8_E5M2 (5-bit exp), FP8_E4M3 (4-bit exp), FP8_E3M4; cFP8 on trn2 has adjustable exponent bias, and only E4/E5 get the double-rate matmul. FIX: Use E4M3 for weights/activations needing precision and E5M2 for range; avoid E3M4 for performance paths.
- Pick the rounding mode explicitly: RNE is the hardware default; enable stochastic rounding with NEURON_RT_STOCHASTIC_ROUNDING_EN=1 (default on in PyTorch-Neuron when XLA_USE_BF16=1) when accumulating small increments into bf16/fp16. FIX: Set the env var at runtime; on trn3 choose RNE or SR for BF16 PSUM downcasts.
- Expect integer matmul, all-reduce, reduce-scatter and scatter-with-compute to be auto-converted to FP32, and 64-bit ints to 32-bit unless --native-int64 (trn2+). FIX: Use int32 indices; compute index math on GpSimd (native 16x int32 per processor) or VectorE.
- Use GpSimd for genuinely integer/low-precision SIMD work: each processor natively does 16x FP32/INT32, 32x FP16/INT16 or 64x INT8 per cycle (VectorE/ScalarE compute only in FP32). FIX: Map int8/int16 element work to GpSimd instructions.
- For MX on trn3: groups of 32 contraction elements share one uint8 scale; quantize_mx produces MXFP8 (not FP4) from BF16/FP16 in SBUF at 4 elements/partition/cycle; MXFP4 inputs are converted to MXFP8 inside TensorE; MXFP8 x MXFP4 mixing is allowed. FIX: Quantize activations with nisa.quantize_mx; keep FP4 weights quantized offline.
- Use TF32 (8-bit exponent, 10-bit mantissa) when FP32 range with more mantissa than BF16 is needed; it runs at BF16 matmul speed on TensorE. FIX: Cast to nl.tfloat32 before nc_matmul.
- When choosing storage dtype for streamed weights, remember the DMA payload floor is in bytes: 2 KiB/partition needs 1024 bf16 or 2048 fp8 elements, so fp8 tiles must be twice as wide to stay DMA-efficient. FIX: Widen fp8 tiles to >= 2048 (ideally 4096) elements per partition.
