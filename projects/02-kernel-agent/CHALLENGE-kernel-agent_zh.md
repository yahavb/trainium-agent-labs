# 挑战任务 — Kernel 编写 Agent

**使用一个每次只能看到 8192 个 token 的模型，构建能够编写芯片级 Kernel 的 Agent。编写 Kernel 是表面上的问题；真正的问题，是决定模型应该看到哪些信息。**

---

## 为什么这件事很难，以及为什么难点不是你想的那样

*Kernel* 是直接运行在加速器上的小程序。你不能只写 `y = softmax(x)`，而需要明确写出将哪些数据块（tile）搬入片上内存、执行哪些计算，以及执行顺序。这是一项专业性强、耗时长的工作，也正是人们如今尝试用语言模型自动完成的工作。

于是你让模型来做，马上就会遇到真正的瓶颈：

| 模型需要看到的信息 | Token 数 |
|---|---|
| Kernel 语言的 API 文档 | 数千 |
| 待实现算子的设计规范 | 一个真实示例约 11,600 |
| 必须匹配的参考实现 | 数百 |
| 当前有问题的 Kernel | 数百 |
| 上一次尝试的错误堆栈与数值差异 | 数百至数千 |
| 分块规则与硬件约束 | 数千 |

**你全部输入信息的总预算只有 8192 个 token。** 这些内容放不下，而且差得很远。

这才是挑战。不是“模型能否编写 Kernel”——它有时确实能——而是**你能否构建一个系统，在每次尝试时判断哪 8000 个 token 最重要？** 每次迭代都要消耗预算。如果把预算花在 API 文档上，模型就看不到自己犯的错误；如果花在错误堆栈上，它就会忘记分块规则，重新发明一种违规实现。

能够解决这一问题的 Agent 将非常有用，而且是在一个尚未被充分探索的方向上取得成果。忽略这个问题的 Agent，大约二十分钟就会遇到瓶颈。

---

## 任务

给定某个算子的参考实现，你的 Agent 需要生成一个**采用分块、显式管理内存的 Kernel**，使其完成相同的计算。然后**运行它、检查数值正确性、读取自身的错误并再次尝试**——整个循环中的每次模型调用都不能超出 token 预算。

### 阶段 A — 在笔记本电脑上运行，无需加速器

使用 **NumPy 编写符合 Kernel 风格约束的程序**。这不是无意义的练习：这些约束正是 Kernel 编写困难的原因，而且都可以在 CPU 上以毫秒级的时间进行检查。

生成的 Kernel 必须遵守：

1. **固定大小的 Tile。** 每个 Tile 最多 `128` 行 × `512` 列，每次处理一个 Tile。
2. **显式遍历 Tile 的循环。** 不允许用整个数组上的运算隐藏分块过程。
3. **禁止高级索引、使用布尔掩码进行索引、`np.einsum` 和利用广播机制取巧。** 只允许切片以及切片上的算术运算。
4. **正确处理无法整除的形状。** 最后一个 Tile 可能是不完整的。多数自动生成的 Kernel 都会在这里悄悄出错。
5. **不能直接调用自己正在实现的算子。** 在 LayerNorm Kernel 中使用 `np.mean` 属于作弊，Checker 会检查这一点。

这些约束刻意贴近真实加速器 Kernel 的限制——固定 Tile 形状、显式数据搬运，以及必须处理不完整的边界 Tile——因此学到的经验可以迁移到真实硬件。

### 阶段 B — 在加速器上运行（进阶目标，仅限有硬件的情况）

使用同一个 Agent 生成芯片上的真实 Kernel 代码，并在设备上验证。**不要从这里开始。** 先在阶段 A 跑通整个循环；Agent 架构完全相同，而反馈速度快一千倍。

## 算子关卡阶梯

逐级挑战。做到一半并如实报告结果，比虚称全部完成更好。

| # | 算子 | 容易踩的坑 |
|---|---|---|
| 1 | `y = relu(a*x + b)`，逐元素操作 | 无——这是验证整个循环能正常工作的检查点 |
| 2 | 二维数组按行求和 | 最后一个 Tile 不完整 |
| 3 | 按行求最大值 | 不完整 Tile；求最大值的单位元是 `-inf`，不是 `0` |
| 4 | 沿最后一维计算 RMSNorm | 累加顺序；float32 与 float64 的差异 |
| 5 | 沿最后一维计算 softmax | **直接计算 `exp` 会溢出。** 必须先减去最大值；错误实现仍可能返回看似正常的数字 |
| 6 | 分块矩阵转置 | 非方阵、不可整除形状下的 Tile 边界 |
| 7 | 带累加的分块矩阵乘法 | 累加器的数据类型；K 维度不能被 Tile 大小整除 |
| 8 | LayerNorm，均值与方差 | 在均值很大时，`E[x²] − E[x]²` 会出现严重的消减误差；测试数据可能正常，实际使用却出错 |
| 9 | 窗口化（带状）Attention，窗口大小为 `w` | 带状窗口边缘；`w` 大于序列长度 |
| 10 | 带步幅和膨胀的 1D 卷积 | 输出大小公式相差 1；末尾的 dilation 处理 |

另外还有三个从相同分布中抽取的关卡，保留用于评审。

**这些错误都可能悄无声息地发生。** 错误的 softmax 可能返回看似合理的数字，错误的 LayerNorm 也是如此，程序不会崩溃。这正是该问题有趣的原因，也是下一节不可跳过的原因。

---

## 不可妥协：验证框架（Verification Harness）

**先构建验证框架，再构建 Agent。** 反过来做的团队会花掉整个下午去调试自己的调试器。

它必须：

* 在**无法被 Tile 大小整除的形状**上与参考实现比较——包括一个质数大小的维度，以及一个长度恰好为 1 的维度。
* 测试**具有挑战性的数值**，而不是容易通过的数值：很大的数值（引发 softmax 溢出）、很大的均值（引发 LayerNorm 消减误差）、零、负数，以及所有元素完全相同的一行。
* 明确说明**数值容差并给出理由**。写出 `rtol=1e-5` 是一个答案；“看起来差不多”则不是。
* **通过静态检查拒绝违反规则的实现**——高级索引、被禁止的函数、超过大小限制的 Tile。违反规则的快速 Kernel 得零分，因此应在评委检查之前自行发现。
* 返回**Agent 真正能利用的错误描述**。“assert failed”无法帮助模型学习；“128 行中的第 47 行，期望值 0.0031，实际值 0.0034，相对误差 0.09，最大误差出现在最后一个不完整的 Tile”则能明确指出检查方向。

最后这一点决定挑战的成败。**错误信息的质量，就是 Agent 的质量。**

---

## 上下文问题的具体表现

每次调用大约只有 8000 个输入 token。到了第 4 次尝试，Agent 可能想提供 API 规则、参考实现、当前 Kernel、最近一次错误、之前三个 Kernel 及其错误，以及已经尝试过的方法列表。内容远远超过预算，因此必须有所取舍。

值得尝试的方法——这也是最有意思的设计空间：

* **分层文档（Tiered Docs）。** 始终附上一张 300-token 的简短规则卡，仅在需要某个特定语法或结构时提供完整文档。
* **错误信息提炼（Error Distillation）。** 将 2000-token 的差异报告浓缩成 50 个 token：哪个 Tile、哪一行、误差方向和大小。可以调用模型，也可以自己编写函数。
* **渐进式披露（Progressive Disclosure）。** 第一次尝试只看到参考实现；根据第一次的错误决定第二次额外提供哪些信息。
* **“已经尝试过什么”的记录表（Ledger）。** 每次尝试压缩成一行，避免 Agent 不断重新提出已经失败的方案。
* **从规则文档中检索信息**，而不是把整份规则直接粘贴进上下文。

无论选择什么方法，都要**加入测量与记录机制**。报告每次尝试使用的输入 token 数，以及 token 的去向。演示时，最有价值的成果之一就是一张图：**每次尝试中，文档、错误上下文和代码分别消耗了多少 token。**

## 关于这个 API Endpoint：否则你会通过失败才学到的事实

以下结论都来自实测；测试方法见 README。

* **输入上限为 8192 token。** 超过限制会收到明确的 HTTP 400 错误。但如果只是*接近*上限，模型输出可能会被悄悄截断，只显示 `finish_reason: "length"`，而不会报错。**每次调用都要检查 `finish_reason`**，否则 Agent 可能会尝试解析只有一半的 Kernel。
* **`max_tokens` 至少设置为 2500。** 模型在输出答案前会先在隐藏的推理通道生成内容。一次编码任务消耗了 900 个 token 思考，最终却返回*空内容*。看起来像拒绝回答，其实不是。
* **采样采用贪心解码（Greedy），直接重试没有意义。** 相同输入会得到字节级完全相同的输出。失败后的重试必须改变 *Prompt*——增加上下文、改变描述方式或缩小问题范围。Temperature 不起作用。没有 best-of-n，也没有 self-consistency。
* **`tools=` 参数不起作用。** 不支持函数调用。需要在 Prompt 中自行约定 JSON 格式，并明确要求提供**最终答案**；否则模型可能在推理通道中完成任务，却不输出任何内容。
* **长 Prompt 的额外开销较小。** Prompt 长度增加 37 倍，延迟仅增加约 15%–20%。可以充分使用上下文窗口，但不要超出上限。
* **所有人共享约每秒 4 次请求。** 一个迭代重试循环的负载，相当于 4–5 个普通聊天用户。要积极使用缓存，不要反复询问已经知道的内容。

## 一个完整示例，以及会耗掉你一整天的陷阱

编写本文档前，我们用这个 Endpoint 测试了第 5 关（softmax），以确认挑战具有可行性。以下是实际发生的情况，因为你很可能在一小时内遇到相同的问题。

**尝试 1——最直接的 Prompt。** 提供参考实现、分块规则、禁止使用的函数列表，以及“你的最终答案必须是一个 Python 代码块”。结果：

```
max_tokens=2500 → finish=length, reasoning=10,194 chars, content=0 chars
max_tokens=7000 → finish=length, reasoning=26,401 chars, content=0 chars
```

**两次都没有返回内容。** 既不是拒绝，也不是错误——模型把全部预算都花在隐藏推理通道上，始终没有开始输出答案。把预算增加近三倍也没有帮助，只是让它思考得更久。查看推理内容就能知道原因：

> *“我们需要确认没有使用 np.sum 或 np.max。我们没有使用被禁止的函数。没有使用高级索引。没有使用全数组操作。使用了 Tile 循环……”*

模型在**逐条审查自己是否遵守了我们给出的每条规则**。问题恰恰来自我们精心编写的 Prompt。即使把禁止性规则改写成正面要求，也没有改善：推理了 13,700 个字符，仍然没有答案。

**为什么它无法自己恢复：采样是贪心的。** 解码过程中没有随机性，因此模型一旦进入重复状态，就没有扰动能让它跳出循环。中途截取到的内容是：

```
We used loops over columns for max. Good.
We used loops over columns for sum. Good.
We used loops over columns for max. Good.
We used loops over columns for sum. Good.
```

这不是缓慢推进，而是陷入了封闭循环。**增加 token 预算无法解决它**——这就是为什么 7000 token 与 2500 token 的尝试都失败了。八次实验中，每个只有一句话的 Prompt 都能在 300–700 token 内生成代码，而所有包含禁止性规则的 Prompt 都陷入了推理循环。

**尝试 2——完全去掉规则。** 只给一句话：“沿最后一维计算数值稳定的 softmax，每次最多处理 128 行。”模型在 617 个 token 内生成了整洁的代码。但它使用了 `np.max` 和 `np.sum`——**违反规则，直接得零分。**

于是你面临两难处境，这也是本挑战真正的核心：

> **明确列出约束，模型就不输出任何内容；省略约束，模型便自信地生成违规代码。**

**真正奏效的方法。** 先让模型直接生成代码，再由*验证器（Verifier）*找出违规之处，然后只发送一条针对性的修改要求，明确指出唯一需要修复的内容——不再附上完整规则、参考实现，只提供代码和这一项修改：

> *“把 np.max 和 np.sum 调用替换成显式遍历列的 Python 循环，分别计算每行的最大值与行和。其他所有内容保持不变。”*

模型输出了 897 个 token。**32/32 个测试用例全部通过，已验证。** 对于有数值溢出陷阱的这一关，只用了两次调用、总计约 1900 个 token。

**还有一次几乎成功的尝试，进一步证明了这一点。** 如果把验证器报告直接*原样*反馈给模型——比如 `line 16: calls banned max`——模型会**再次违反同一规则**。报告指出了哪里错，却没有告诉模型该怎么改。将其改写为上面的明确指令后，一轮就修好了。从“判定结果”到“修改指令”的转换，是 Agent 能做的最有价值的事情。

这一经验可以推广：**约束应该放在验证器中，而不是生成阶段的 Prompt 中。** 模型不擅长同时记住十条规则，却擅长执行一项具体的修改。Agent 的职责就是把“这里错了”转换成“只修改这里”。

这只是一个关卡。后面还有九关，以及三个保留的评审关卡。更难的第 8、9、10 关不会靠一次修改就轻松通过。不过，现在你已经明白问题的基本结构，这比我们一个小时前知道的还多。

## 评分标准

与其他挑战采用相同的评分方式。

| 权重 | 项目 | 评分内容 |
|---|---|---|
| **30%** | 正确性（Correctness） | 在**保留测试形状和具有挑战性的数值**上通过了多少个关卡，而不仅仅是你自己的测试。违反规则即为零分，而不是扣掉部分分数。 |
| **25%** | 交付结果（Delivered Result） | 完成的关卡数，以及每关通过所需的尝试次数。越少尝试便成功，说明 Agent 设计越好，而不只是运气好。 |
| **25%** | 方法与诚实性（Method & Honesty） | **Agent 是否知道自己什么时候失败？** 对无法通过验证框架的 Kernel 宣称“已验证”，比诚实报告失败得分更低。此外还考查 token 预算的监测记录和失败类型分类。 |
| **20%** | 演示与报告（Demo & Write-up） | 展示一次失败及其恢复过程，而不只是成功案例。其他人能否复现？ |

### 区分顶尖团队的两件事

**置信度校准（Calibration）。** Agent 必须输出置信度，并且置信度要与真实情况相符。在错误 Kernel 不会崩溃的任务中，自信地给出错误结果是最糟糕的行为——在生产环境里，这意味着将隐蔽的数值错误交付给用户。说“我无法验证第 8 关”的 Agent，比谎称“已完成”的 Agent 更有价值。

**失败类型分类（Failure Taxonomy）。** 让 Agent 跑完整个关卡阶梯，收集生成过的所有错误 Kernel，将它们归纳成少数几种有名称的失败模式。失败发生在哪些关卡？*为什么*失败？是误解了 Tile 规则、忘记处理最后一个不完整 Tile、重新使用了违规索引方式，还是修复了被指出的错误却破坏了另一部分？这是一项分析工作，不需要加速器，也是组织者最希望保留下来的成果。

## 需要提交的内容

1. **Agent 本体。**
2. **验证框架（Verification Harness）**——明确数值容差及其设计依据。
3. **评估测试集（Eval Set）**——所测试的形状和数值，包括具有挑战性的测试值。这是强制要求。
4. **失败类型分类（Failure Taxonomy）**——将错误分组，并给出每类的出现次数。
5. **Token 使用情况的测量记录**——每次尝试使用的输入 token 数，以及各部分分别用了多少。
6. **一页复现说明。**

## 从哪里开始：按以下顺序进行

1. 编写第 1–3 关的参考实现和验证框架。**现在先不要调用模型。**
2. 自己手写一个正确的第 1 关 Kernel，确认能通过验证框架；然后故意引入错误，确认验证框架能发现问题，**并生成有帮助的错误信息**。如果连你故意制造的错误都抓不到，也就不可能抓住模型生成的错误。
3. 现在接入模型。先只调用一次，让它尝试第 1 关。
4. 添加失败重试循环，之后再开始关注 token 预算问题。
5. 逐级挑战。

## 合理的预期

第 1–4 关可以完成。第 5–7 关完成后，算是收获很大的一天。第 8–10 关难度很高，尤其第 9 关确实非常难。

**一个通过四关，并对其余六关失败原因提供严谨分类的团队，会胜过一个声称完成第 9 关、却无法展示验证过程的团队。** 这不是安慰奖，而是评分标准本身。
