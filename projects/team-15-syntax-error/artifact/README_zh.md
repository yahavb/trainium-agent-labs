## 一、一句话说清楚我们做了什么

**模型一整天没换（Qwen3-8B，跑在我们自己的 Trainium 芯片上），我们只改了"检查器在模型出错时说的话"，并在外面加了一层由 Claude 担任审核员的循环。结果，8B 小模型写芯片 kernel 的能力从"4 级一级都过不了"变成了"8 级稳定过 7 级"。**

---

## 二、比赛是什么（"上游"指什么）

- **比赛**：NYU × Annapurna Labs（AWS 自研芯片团队）的一日黑客松 "Hack the Chip"。
- **"上游"**：比赛方提供的起始仓库 `yahavb/trainium-agent-labs`，里面有：
  - 一块 **Trainium 芯片** + 上面跑的小模型 **Qwen3-8B**；
  - 一个 **agent 循环**：模型写代码 → **检查器**打分并说明错在哪 → 把说明喂回模型 → 模型再试；
  - 一个 **8 级阶梯**（我们叫 Stage B），题目是让模型写 **NKI kernel**，也就是直接在芯片上运行的底层计算程序；
  - 一个 **10 级的 NumPy 阶梯**（Stage A），用 NumPy 按"kernel 的规则"写，纯 CPU 检查。
- **比赛的核心论点**：成败取决于**检查器的反馈质量**，而不是模型本身。一句"错了 341%"是真话但没用；一句"这一项根本不该存在"才告诉模型改哪里。

### 8 级阶梯分别考什么

| 级 | 内容 | 考什么 |
|---|---|---|
| L1 | 平均池化 | 能不能写出合法的芯片代码 |
| L2 | 转置 | 数据在芯片上的布局 |
| L3 | 单块矩阵乘 | 矩阵乘的硬件规则 |
| L4 | 分块矩阵乘 | 大矩阵切成小块来算 |
| L5 | 矩阵乘 + 加载外提 | **算对之外**，从内存搬运的数据 ≤ 理论最小值的 1.90 倍 |
| L6 | 矩阵乘 + M/N 分块 | 搬运量 ≤ 1.30 倍 |
| L7 | 矩阵乘 + 全分块 | 搬运量 ≤ 1.05 倍（几乎不能有任何重复搬运） |
| L8 | 单头注意力 | 两次矩阵乘中间夹一个数值稳定的 softmax |

L5–L7 的计算和 L4 一模一样，**比的是"省着搬"**，因为芯片大部分时间花在搬数据上，而不是计算上。

## 三、问题出在哪里

我们读了模型的近 2000 次尝试，发现问题分三类：

1. **检查器的话"对，但不是指令"**
   - 例子：模型把 `lhsT[k, m]` 写成了 `lhsT[m, k]`（两个轴写反）。在方形数据上它**不报错，只是悄悄算错**。
   - 上游检查器只会说"大部分元素错了，检查一下布局"，模型看不懂该改哪里，就一直重复同样的错。
2. **检查器的话"有误导"，比模糊更糟**
   - 模型只是忘了把数据拷进去，检查器却说"可能是读了未初始化的 tile"。
   - 模型于是去发明 `nisa.psum_zero` 这种不存在的函数，追着一个不存在的问题跑。
3. **上游自己的提示就是病根**
   - **L6**：上游给 L6 的提示"分块复用"，把模型引向了错误的循环顺序。
   - **L8**：API 卡上只列了 `nl.sum`，结果 115 次尝试全部用错了归约操作。

## 四、我们的方案：两层循环（核心创新）

```
┌────────────── 内循环（比赛本来就有，每一轮都跑）──────────────┐
│  代码 → agent 写 kernel → 检查器打分 → 把"错在哪"翻译成"改哪里" → 回到 agent  │
└───────────────────────────────────────────────────────────────┘
                    ↓ 卡住了（一直 0 分 / 反复同样的错 / 变差）
┌────────────── 外循环（我们的创新）──────────────────────────────┐
│  Claude 在代码之外当审核员：对照"agent 是怎么修的"和"这一级真正要什么"│
│  → 提出一条新指令 → 先验证可行 → 在芯片上做对照实验 → 有效才作为新开关上线 │
└───────────────────────────────────────────────────────────────┘
                    ↓ 回到内循环
```

**关键点**：
- **每一条新指令都先验证再用**：要么我们手写一个能通过的 kernel，证明这条路走得通；要么确认它不会误伤任何正确的代码。
- **每一个改动都做对照实验**：同样的设置，一组用旧提示（对照组），一组用新提示，各跑 5 次，用成功率说话。
- **没用的改动会撤回**：文档检索（E2）、AST 自动修复（E3）、给 L8 的 v10 都被放弃了，原因都写在 LOG.md 里。

## 五、具体改了什么，各自效果如何（每级 5 次，[sim]）

| 改动名 | 做了什么 | 效果 |
|---|---|---|
| 骨架 `--skeleton` | 给模型一个带"待填空"的代码框架（不是答案） | L2：0 → 5/5 |
| **v2** | 检查器**读模型的代码**，发现轴写反就直接说"应该写成 `lhsT[k0:…, m0:…]`" | **L3、L4：0 → 5/5** |
| **v3** | L1：告诉模型"把每个池化窗口归约成一个 (C,1) 的 tile" | **L1：0 → 5/5** |
| **v4** | L5："lhsT 的加载跟 n 无关，移出 n 循环" | **L5：0 → 5/5**（对照组 0/5） |
| **v5** | L5–L7："每个 tile 只从内存加载一次" | **L7：0 → 5/5**（对照组 0/5） |
| v7 / v8 / 提示修正 | 指出"数据没拷进去"、"k 循环放错位置"；把 L6 的误导提示换掉 | **L6：0 → 5/5** |
| v9 | 在模拟之前对照真实函数签名，**一次列出所有调用错误** | 省掉好几轮 |
| 设备规则 | 禁止列表推导式（模拟器能过，真芯片编译不过） | L7 的写法符合芯片要求 |
| 修正上游工具 | 按 AWS 官方 kernel 实测重定 L5/L6 门槛；修好 L8 的崩溃 | 阶梯本身变得可信 |

## 六、最终成绩

### Stage B（NKI，8 级）：最终版 agent "C10"

| 第几轮解出 | 2 | 1 | 2 | 2 | 4 | 3–4 | 3 | — |

### 其他成绩
- **Stage A（NumPy，10 级）：解出 9 级**，只剩 A5（softmax）。
- **真芯片 [device]**：agent 写的 L3、L4、L5 kernel 在 Trainium2 上运行正确（误差 1e-6）。
- **刁钻测试**：agent 以 0.95 置信度声明"解出"的 **31/31** 全部通过它没见过的测试；**AWS 官方教程的 kernel 反而过不了**，其中一个在 K=131 时静默算错。
- **置信度校准**：Brier 分数 **0.030**（越接近 0 越准，n=38）。
- **重新评分**：支撑主要决定的 354 次尝试，用它们自己的代码重新评分，**0 处不一致**。

### 诚实说明（局限）
- **L8（注意力）没解出**：经过 4 轮审核，模型已经推进到 softmax 这一步，但仍在循环。
- **没有报运行速度**：kernel 在芯片上算得对，但没测到芯片内部的计时。
- **"5 次"不完全独立**：服务器的输出是确定性的。Stage A 的重复运行完全相同，所以实际相当于 1 次。
- **L1 最不稳定**：把所有最终配置的运行合起来是 17/20。
- **L2 的骨架提示比较强**：几乎说出了转置的下标规律，所以 L2 算"强提示下解出"。

## 九、常用词对照

| 英文 | 中文意思 |
|---|---|
| checker | 检查器：给模型的代码打分，并说明错在哪 |
| verdict / instruction | 判定（"错了"）/ 指令（"改这一行，改成这样"） |
| kernel | 直接在芯片上运行的底层计算程序 |
| NKI | AWS 给 Trainium 芯片写 kernel 用的语言 |
| Trainium | AWS 自研的 AI 芯片 |
| skeleton | 骨架：带"待填空"的代码框架 |
| A/B test, control | 对照实验；control 是对照组 |
| memory traffic / bytes / floor | 从内存搬运的数据量 / 理论最小值 |
| held-out tests | 模型从没见过的测试，防止"刚好过公开测试" |
| calibration / Brier | 置信度是否准确；Brier 越接近 0 越准 |
| regrade | 用代码重新评分，检查结果是否被污染 |
| ADOPT / REVERT | 采用 / 撤回 |
| seat | 座位，也就是一台带芯片的 pod（我们用了 70–74 共 5 台） |
| [sim] / [device] | 模拟器结果 / 真芯片结果 |
