How it works

A sentence in, a checked chip design out, with live Trainium metrics closing the loop.

gpt-oss-20b, served on one Trainium2 seat, designs an accelerator for the workload it is serving. A checker built from that chip's own vLLM and Neuron trace measurements grades every attempt, and the grade plus the reason become the next prompt.

03 · Why not an if-else?

A rule knows the direction. The loop finds the trade.

The obvious rule is already inside the checker, as its diagnosis. On its own it optimizes the wrong thing as soon as the objective or the budget changes.

The rule

# "decode is memory-bound, so add bandwidth"
if decode_bound == "memory":
    hbm_bandwidth *= 1.2
elif prefill_bound == "compute":
    tflops *= 1.2
Latency advice on Cost-down640 mm²
Checker-led loop294 mm²
Fixed-rule proposer (chat)1 of 3 edits helped

Black tick = today's 457 mm² die. Real runs on seat-32: following latency advice on a cost objective grew the die to 640 mm², while objective-aware checker feedback shrank it to 294 mm² with p99 TTFT and throughput no worse. The repo's deterministic rule-based proposer (ACCELTWIN_MOCK_LLM=true) applies fixed edits, ignores the checker's reason, and stalled after one useful edit.

Every knob moves several limits at once

11architecture knobs per design (cores, clusters, TFLOPS, HBM GB / TB/s / stacks, SRAM, DMA, utilization, power, cooling)
5blocksregion choices per block, plus a wiring graph whose max-flow decides usable bandwidth
6hard gates that interact (throughput, memory fit, power, temperature, area, layout) under 5 different objectives
1 sentenceis all the user gives: the model turns it into a plan, the checker turns results back into the next instruction

Honest scope: this is architecture exploration in a simulator calibrated to the live chip, not a measurement of new silicon. One run per scenario so far, so no spread is reported yet. Rankings between designs are more trustworthy than absolute milliseconds.
